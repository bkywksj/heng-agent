# 安全重构

重构 = **只改结构、不改行为**。用户看得见的结果、接口、输出都要和原来一样；要改行为是另一件事，分开做。

## 1. 先确认有兜底

- 找到覆盖这段代码的测试，先跑一遍、确认全部通过——这是「行为没变」的依据；
- 没有测试就先补（按 writing-tests 技能），至少覆盖主要路径与边界，再动手重构；
- 实在补不了测试的，跟用户说明风险，改得更保守。

## 2. 弄清楚影响范围

- 搜出所有调用方（函数、类、配置项、导出的接口），重命名或改签名时一个都不能漏；
- 注意不容易搜到的引用：字符串里的名字、反射与动态调用、配置文件、模板、文档、其他仓库对公开接口的依赖；
- 公开接口（别人在用的）不要随意改；必须改的，保留旧名字并标注为过时，或者先和用户确认。

## 3. 小步走

一步只做一种改动，每步之后都跑测试：

1. 重命名（变量、函数、文件）；
2. 提取函数 / 提取变量；
3. 移动代码（拆文件、换模块）；
4. 去掉重复（合并相似的代码）；
5. 简化条件、去掉死代码。

不要把重构和修 bug、加功能混在同一步里——出了问题分不清是哪一部分造成的。

## 4. 收尾

- 全部测试通过；跑项目的代码检查与格式化工具（如果有）；
- 删掉重构后不再使用的代码、导入与文件；
- 向用户说明：改了什么结构、为什么这样更好、怎么确认行为没变（跑了哪些测试）。

## 不要做的

- 一口气大改、最后才跑测试；
- 顺手「改进」行为（改默认值、改报错文字、改输出格式）；
- 没让改的地方也改（只动用户要求的范围，看到别的问题提出来、不擅自动手）。
