# 写测试

## 1. 先看项目怎么测

动手前先弄清楚，**照着现有的写**，别引入新的测试框架或风格：

- 用什么框架、怎么运行（看 `package.json` 的 scripts、`pyproject.toml`、`Makefile`、CI 配置、项目说明文件）；
- 测试放在哪、文件怎么命名、已有的测试长什么样（挑一两个读一读）；
- 有没有现成的工具函数、夹具（fixture）、假数据、模拟对象可以复用。

## 2. 想清楚测什么

针对要测的那段代码，列出：

- **正常路径**：典型输入得到期望输出；
- **边界**：空值、空列表、零、负数、最大值、刚好在临界点上（如「满 99 包邮」测 98.99、99、99.01）；
- **出错情况**：非法输入、依赖失败（网络、文件、数据库）时，是否按设计报错或降级；
- **刚修的 bug**：写一个修复前会失败的测试。

每个测试只验证一件事，名字说清楚在测什么（如「满 99 元包邮」，而不是「测试 1」）。

## 3. 写得可靠

- 不依赖执行顺序、当前时间、随机数、真实网络、本机的特定文件：需要就固定下来或模拟掉；
- 用临时目录，测试结束不留垃圾，不碰用户的真实数据；
- 断言要具体：断言确切的值或关键字段，而不是只断言「不为空」「没有报错」；
- 只模拟外部边界（网络、时间、第三方服务），被测的逻辑本身不要模拟掉，否则测了个寂寞。

## 4. 跑起来

- 先单独跑新写的测试，确认通过；再故意把被测代码改错一处，确认测试**会失败**（证明它真的在检查）；
- 最后跑一遍全部测试，确认没有影响别的；
- 告诉用户加了哪些测试、各覆盖什么情况、怎么运行。

## 不要做的

- 为了让测试通过而去改被测代码的行为（除非那就是 bug，并说明）；
- 写一堆只覆盖到代码行、却不检查结果的测试；
- 测试失败时直接删掉或跳过它。
