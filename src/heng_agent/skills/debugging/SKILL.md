# 排查问题

目标是找到**根因**，不是让报错消失。在找到根因之前改代码，常常只是把问题藏起来。

## 1. 复现

- 先拿到能稳定复现的步骤：哪条命令、哪个输入、哪个测试。用户给的报错信息完整读一遍，别只看最后一行。
- 能写成一个失败的测试最好——它既是复现手段，修好后又是回归测试。
- 复现不了时，先收集信息（日志、版本、环境差异），不要凭猜测改代码。

## 2. 定位

- 从报错位置往回读调用链，弄清数据从哪来、在哪一步变得不对。
- 用二分缩小范围：最近哪次改动引入的（`git log`、`git bisect`）、哪一段输入触发的、哪一步之后状态不对。
- 加临时的打印或断言确认假设，**一次只验证一个假设**；确认后再往下走。
- 时好时坏的问题，先怀疑：并发与竞态、缓存、时区与时间、依赖外部服务、测试之间互相影响、平台差异（路径分隔符、换行符、编码）。

## 3. 找到根因

能说清楚「为什么会出错」才算找到根因：哪个前提不成立、哪段代码在什么情况下给出了错误结果。
如果解释里有「大概」「可能」，说明还没找到，继续定位。

## 4. 修复

- 修根因，不修症状：别用 `try/except` 吞掉异常、别加特判绕过某个输入、别把断言删掉让测试变绿。
- 改动尽量小，只改和根因有关的部分；顺手看到的别的问题记下来、单独处理。
- 想一想同样的错误会不会出现在别处（同一个函数的其他调用方、相似的代码），一起查。

## 5. 防止再犯

- 加一个回归测试：修复前失败、修复后通过。
- 跑相关的全部测试，确认没有改坏别的。
- 向用户说明：现象、根因、改了什么、怎么验证的。根因不是代码问题（如配置、环境、数据）时，说清楚该怎么处理。

## 不要做的

- 没复现就改代码、改完说「应该好了」；
- 一次改好几处、分不清是哪处起作用；
- 为了让测试通过而修改测试的期望值（除非确认期望值本身是错的，并说明理由）。
