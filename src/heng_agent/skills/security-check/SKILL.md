# 安全检查

默认只检查、只报告，不擅自修改；用户要修再修。范围不明确时，先看这次的改动（`git diff`、`git diff --staged`），
用户要求时再扩大到整个项目。

## 检查清单

**密钥与敏感信息**
- 代码、配置、测试数据、日志、报错信息里有没有写死的密码、API 密钥、令牌、私钥、连接串；
- 这些东西会不会被提交进仓库（看 `.gitignore`）、打印到日志、返回给前端。

**注入**
- SQL：有没有把用户输入拼进 SQL 字符串（应使用参数化查询 / ORM 的参数绑定）；
- 命令：有没有把用户输入拼进 shell 命令（应传参数列表、不经过 shell）；
- 页面：用户输入直接输出到 HTML 有没有转义（XSS）；
- 路径：用户给的文件名或路径有没有做限制（`../` 越出目录）；
- 其他：模板注入、反序列化不可信数据、正则表达式被恶意输入拖垮。

**认证与权限**
- 每个接口是否检查了登录、是否检查了「这条数据是不是这个人的」（越权访问别人的数据）；
- 前端的校验不能代替后端的校验；
- 密码有没有用专门的哈希算法存储（如 bcrypt、argon2），而不是明文或普通哈希。

**输入与输出**
- 外部输入（请求参数、上传文件、第三方回调）有没有校验类型、长度、格式；
- 上传文件有没有限制类型与大小、存放位置能不能被直接执行；
- 报错信息有没有把内部细节（堆栈、SQL、路径）暴露给用户。

**依赖与配置**
- 有没有明显过时、已知有漏洞的依赖（项目有审计工具就运行：`npm audit`、`pip-audit` 等）；
- 调试开关、默认账号密码、过宽的跨域（CORS）配置有没有带到生产环境。

## 报告格式

按严重程度从高到低列出，每条写清楚：

- **位置**：文件与行号；
- **问题**：是什么、在什么情况下能被利用、会造成什么后果；
- **修法**：具体怎么改（给出示例代码）；
- **严重程度**：高（能直接被利用、泄露数据或执行代码）/ 中（需要特定条件）/ 低（加固建议）。

没发现问题就明确说没发现，并说明检查了哪些范围——不要为了「有发现」而夸大问题。
