# 经验沉淀

不沉淀的话，踩过的坑只存在聊天记录里：换一个会话、或另一个会话并行开发，同样的坑会再踩一遍
（`console.export_text()` 清空内容这个坑就在两个测试里各踩了一次）。

## 步骤

1. **回顾**：看这次会话做了什么；或 `git log --oneline -10` 与相关提交的 diff。
2. **挑出值得记的**：只记「下次还会遇到、而且不看记录就会再犯」的。按下面六类归类。
3. **去重**：先搜一下（`grep -rn 关键词 CLAUDE.md .claude/skills docs/experience`），已经写了的就补充、不重复写。
4. **写到对的地方**（见下表），用 ❌ / ✅ 或「现象 → 原因 → 做法」的写法，具体到文件名、函数名、命令。
5. **新增或改了技能**：更新 CLAUDE.md 的「技能索引」。强制评估钩子每次自动读 `.claude/skills/`，不用改它；
   但技能的 description 里要有「触发场景：」一行，钩子靠它告诉模型什么时候用。
6. **告诉用户**沉淀了哪几条、写在哪里；和功能改动分开提交（提交信息「沉淀经验：…」）。

## 六类经验与去向

| 类别 | 识别信号 | 写到哪里 |
|---|---|---|
| 禁止的做法 | 「这样写会出错 / 静默失效 / 卡住」 | CLAUDE.md「绝对禁止」表格加一行（❌ / 为什么 / ✅） |
| 必须遵守的规则 | 影响安全、数据、协作的硬性约束 | CLAUDE.md 对应的 🔴 小节 |
| 改动清单漏项 | 「改了 A 还得改 B，这次漏了」 | feature-checklist 技能对应的表格 |
| 验证方法 | 「这种改动单元测试测不出来，得这样实测」 | test-development 技能 |
| 某个领域的门道 | 协议差异、终端编码、兼容约定…… | 对应技能；还没有合适的技能，就先记进 docs/experience，攒够三条再考虑新建技能 |
| 一次性的排查过程 | 难查的 bug 怎么一步步定位到的 | `docs/experience/YYYY-MM-DD-主题.md`（现象、排查过程、根因、修法、怎么防止再犯） |

## 不要记的

- 代码里一看就知道的东西（函数做什么、参数是什么）；
- 一次性的、以后不会再遇到的；
- 没验证过的猜测——要记就写明「未验证」。

## docs/experience 的记录格式

```markdown
# 主题（一句话）

- 日期：YYYY-MM-DD　相关提交：xxxxxxx

## 现象
## 排查过程
## 根因
## 修法
## 怎么防止再犯（加了什么测试 / 规则 / 清单项）
```
